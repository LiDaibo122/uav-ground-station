# Qwen 原生工具调用与固定翼调度

当前链路为：用户自然语言 → Qwen 原生 `tool_calls` → 地面端工具执行 → 工具结果返回模型 → 模型继续调用或回答。主对话没有“命中起飞关键词就绕过模型”的分流，也没有固定 action 分类再用关键词覆盖。工具说明定义功能与参数；用户无需背诵工具名或固定话术。

## 运行

```bash
cd /home/ldb/ground_station
GAZEBO_IP=127.0.0.1 QT_QPA_PLATFORM=xcb LIBGL_ALWAYS_SOFTWARE=1 \
  python3 -m packages.swarm_sim.demo --hold --gui
```

打开 http://127.0.0.1:11843/?mode=live&swarm=1 ，等待三架固定翼上线。此入口不预装巡检点；`--fixture` 才是旧六点回归。可用自己的现代浏览器打开网页。

`--gui` 入口默认进入 tmux，提供状态、位置、电量、任务、Qwen 和 MAVROS 检查窗口；详见 [tmux 监视说明](TMUX_CONSOLE.md)。临时直接运行可加 `--no-tmux`。

下面是示例，并非必须使用的命令句式：

```text
现在谁还在地上，谁已经离地了？
先让一号上天转一会儿，另外两架先别动。
刚才那架先在附近绕着，别继续跑任务。
让它回去吧，另外两架不用管。
```

另一段多轮方案对话：

```text
先帮我算算：东边一公里、北边两百米那个点要尽快检查。
三号机先留着，暂时只看方案。

再拿匈牙利和基础拍卖比较一下，别真的发给飞机。

刚才那个点改成常规优先级，三号现在也可以参与，其他不变。

行，就按你刚改的那个来，开始干吧。
```

模型将中文距离换算为局部米数，东/北为正、西/南为负，原点为经度 103.565、纬度 31.045；也支持显式经纬度及地图已有区域。没有任意地名地理编码服务，无法确定“那边河道”时应追问具体位置。坐标系和任务语义由模型判断，执行端再校验数值和范围；不再用原文坐标正则决定模型意图。因此仍需检查方案卡，不能假定小模型对任意表达都可靠。

## 可调用工具

| 工具 | 功能 | 是否操作飞机 |
|---|---|---|
| `get_fleet_state` | 实时位置、电量、模式、离地状态、载荷和遥测文本 | 否 |
| `get_mission_status` | 执行状态、已到点和剩余目标 | 否 |
| `get_plan` | 读取本会话已有方案，解析后续修改 | 否 |
| `plan_inspection` | 新建或修订点、优先级、载荷、飞机范围和算法 | 否 |
| `compare_allocations` | 同一遥测快照实算多种分配算法 | 否 |
| `execute_plan` | 读取最新状态重新分配并上传方案 | 是 |
| `takeoff_aircraft` | 为指定地面飞机生成起飞与等待航段 | 是 |
| `control_aircraft` | 盘旋等待、继续原任务、PX4 返航 | 是 |

工具目录随会话和运行状态提供：没有方案时不提供读取/执行旧方案的工具，没有空中飞机时不提供模式控制工具。演示模式不提供执行工具。工具参数接受类型、范围、载荷、实时状态等检查；模型不能任意调用 shell 或生成未经定义的 MAVLink 指令。

扩展功能时，在 `agent_tools.py` 注册工具参数和描述并接入处理函数，模型在同一个推理循环里选择它。将来机载小模型/世界模型的观测可通过状态工具输入，ROS 通信适配器可替换现有 Session 执行器，无需建立新的用户口令表。

## 算法与 PX4 映射

| 算法 | 当前实现范围 |
|---|---|
| CBBA | 多任务 bundle、每机最多 2 点、优先级、电量与载荷参与出价 |
| 匈牙利 | 一对一匹配，任务数不超过可用飞机数 |
| 基础拍卖 | SSlap 源码实现的一对一匹配；矩形输入先补齐虚拟任务 |
| 贪心 | 按优先级逐点选择可行飞机、每机最多 2 点 |

CBBA 出价为“任务价值 × 到达时间衰减 × (0.5 + 0.5 × 电量比例)”，高/常规/低优先级价值为 2000/1000/500。未知电量、低于 25% 电量、过期状态或不满足载荷/飞机限制的飞机不参与。基础匹配使用按电量修正的直线到达时间成本。不同目标函数的结果不能仅凭一项航程宣称谁更优。

比较工具使用同一快照；任务数不超过可用机数时采用每机 1 点比较，多任务场景每机 2 点。它返回真实分配与直线航程/估计时间，不计起飞、固定翼转弯、地形或风，不能当作可飞轨迹证明。CBBA 当前在地面单进程模拟共识，尚未实现机间竞价通信。

模型选取高层工具，执行适配器负责已有控制协议：

- 任务/起飞：生成 `MAV_CMD_NAV_TAKEOFF`、航点、盘旋及合法备选降落航段，完成 Mission 上传握手，再切任务模式、按需解锁。
- 等待：`MAV_CMD_DO_SET_MODE` → `AUTO.LOITER`。
- 继续：`MAV_CMD_DO_SET_MODE` → `AUTO.MISSION`。
- 返航：`MAV_CMD_NAV_RETURN_TO_LAUNCH` → PX4 自身返航程序。

`queued`、Mission ACK 或 COMMAND_ACK 均不能证明起飞/到点。以解锁、landed、相对高度、速度和任务到点遥测确认实际阶段。地面未解锁飞机也可能显示 `AUTO.LOITER`。固定翼等待时持续前飞盘旋，不能原地悬停。

已有巡检方案包含起飞，不必先单独起飞。任务中需替换方案时，先查询进度并让相关飞机盘旋暂停，再规划、执行新方案；空中接续不重复加入起飞段。局部暂停时其他飞机继续运行，不会自动重分配其任务。失联自主处置仍由机载端负责。

## 界面、日志与验证

界面显示实际工具调用进度、参数与返回值；分配表、比较数值直接来自算法结果，避免依赖模型复述数值。执行进度来自 PX4 遥测。会话保存在 `runs/conversations/<conversation_id>.json`，网页清空对话会建立新会话；仿真与各轮执行记录在 `runs/interactive/<session_id>/`。

模型输入每步重新打包，历史工具结果摘要化、旧遥测去重，并预留生成空间。原始工具结果和用户会话记录仍保留；实际token用量可在tmux的qwen窗口查看。原因与复测见 [上下文管理说明](CONTEXT_MANAGEMENT.md)。

```bash
npm test
npm run build
python3 tests/evaluate_qwen_tools.py --model qwen3.5:2b
python3 tests/evaluate_qwen_tools.py --model qwen3.5:4b --report qwen-agent-evaluation-4b.json
```

模型评测使用真实本地 Qwen、原生工具调用和真实算法，但飞控工具接入 dry-run fixture，不启动飞机。报告明确记录这一边界；不能用其通过率代替真实 PX4 飞行验证。模型有误解、漏调用和文字幻觉的可能，增加工具不等于获得任意自然语言可靠性。

## 当前仿真边界

平地 Gazebo 物理场景，每轮最多 6 点、原点 2.5 公里内；网页山地仅作地理可视化。区域生成 3 个内侧样点，不保证完整面积覆盖。相机、热成像识别、避碰、完整覆盖航迹和 ROS 机载控制协议未接入；thermal 为场景能力声明。遥测文本由 `observations.py` 确定性生成，不是已实现的世界模型。

PX4 v1.13.3 独立实例 1/2/3，端口 14541/14542/14543、系统 ID 2/3/4；业务编号 FW-01/02/03。启动钩子 `px4-rc.params` 设定首航点距离 3500 米等仿真配置，执行阶段不改写这些参数；地面端 2.5 公里范围仍保留。电池过期或空速/地速持续异常会标记 `sensor_error`。

原生工具协议参考：[Ollama tool calling](https://docs.ollama.com/capabilities/tool-calling)、[Qwen3.5-2B 官方模型卡](https://huggingface.co/Qwen/Qwen3.5-2B)。
