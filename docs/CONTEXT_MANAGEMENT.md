# Qwen 上下文空间与三点规划截断

2026-11-15 用户输入三点规划、明确不要执行后，实际只完成 get_fleet_state，没有生成新方案。该轮输入本身128字符；旧打包方式却带入6轮完整历史（约32K字符），包含重复失败、旧机群快照和原始工具返回。

Ollama 日志记录第二步输入16245 token，窗口16384；只生成139 token便用满窗口。此次的 done_reason=length 是上下文没有生成余量，不能解释成4096生成额度本身耗尽。16K是当前运行配置，不能把它说成4B模型天然的最大上下文。

## 当前处理

- 每次模型调用重新打包，而非只按字符截取历史。
- 窗口保持16384，开启思考时预留4096生成token与1024安全余量；发送前的输入预算为11264。
- 历史工具结果转换为摘要，旧遥测明确标记历史，不重放为当前状态；用户需求、方案目标、飞机选择、执行回执保留。
- 当前机群快照合并重复的aircraft/planning_fleet/观测摘要；保留真实飞行状态、坐标、电量、时效、能力，实际地速与规划速度分开。
- 完整工具结果继续供前端展示并保存在会话文件，压缩只影响传给模型的内容。
- 必要输入仍装不下时，停止新增请求并保留已有回执；不会通过截断用户坐标或扩大执行范围强行继续。

输入预算使用明确标注的保守估算，并非模型精确分词。每步另记录Ollama返回的真实prompt_eval_count、eval_count、done_reason；实际计数用于诊断和回归。tmux的6号qwen窗口显示实际输入/生成和打包估算，二者分别标明。

截断时区分上下文用满与生成达到限额。若该轮只读取状态，明确说明尚未生成新方案。API的plan_created_this_turn、plan_origin区分本轮新方案和会话里的旧方案，避免把旧草案误认为当前规划成功。

## 2026-11-16 自动压缩与推理耗时复核

“模型到上下文上限会自动总结”并不是直接调用推理API的保证。语义摘要由聊天产品或Agent应用组织；llama.cpp的context-shift只是KV token删除/移位，也不等于语义摘要。本机日志还明确记录 `KV cache shifting is not supported for this context, disabling KV cache shifting`，所以不能根据启动参数中有context-shift就假定它实际可用。当前应用的context.py已经负责历史摘要与预算管理，原始存档仍保留。

旧提示“模型本轮生成达到长度上限…”是agent.py在收到停止原因后拼接的controller文案，不是Qwen主动生成拒答。最新保存的实际用户会话adbb...最后三步输入3567/4481/4714 token，均done_reason=stop，没有修复后再次撞满窗口的证据。4B是模型参数量，当前16K是运行配置，不代表模型元数据最大上下文只有16K。

最近四轮记录共九次Ollama调用，单次约2.95–13.81秒；一次规划/执行/状态/返航通常包含2–3次调用。当前stream=false会在整轮完成后返回，因而约8–19秒的聊天等待与地图帧率卡顿是两类问题。现有数据是历史日志分组，不是独立性能基准。
